# Platform builds and releases

Status: target design from `docs/architecture/omni-plan.md` §6 (2026-10-31). Each variant ships to six targets: iOS, Android, web (Docker image), Electron win/mac/linux.

## Native (EAS)

- One Expo project (`apps/omni`), **five EAS projects** (credentials, push keys and store bindings stay per app). `app.config.ts` sets `extra.eas.projectId` from the variant manifest.
- `eas.json` profiles are `<variant>-<profile>` (`production`, `production-apk`, `staging`, `staging-store`, `staging-apk`, `internal`, `internal-store`, `internal-apk`, `development`, `dev-sim`, `simulator`) with `APP_VARIANT`/`APP_ENV` in `env`, `EXPO_NO_DOTENV=1`. Generated by `pnpm eas:generate`; never edit `eas.json` by hand.
- **Signing credentials live on EAS only** (owner decision, plan §15 #19). No profile sets `credentialsSource: local`; `eas build --local` downloads the Android keystore and iOS certificate/profiles with `EXPO_TOKEN`. Never add a keystore, `credentials.json`, `.p12` or `.mobileprovision` to CI secrets or the repo.
- Ad-hoc iOS builds are made on a Mac, not in CI: `pnpm ios:adhoc <variant>` (`scripts/build-ios-adhoc.mjs`, profile `<v>-internal`, env from the shell or `.env.<variant>`, output in `dist/ios-adhoc/`).
- Credentials: `pnpm credentials:<android|ios|ios-adhoc> <variant> [--env staging|development] [--setup]` (`scripts/eas-credentials.mjs`) runs CI's eas-cli with the emit's profile env and names the profile to pick (`--setup` = `credentials:configure-build` for exactly that profile). Staging and development builds have their own bundle ids/packages (`.staging`, `.development`), so their own credentials.
- Always export `APP_VARIANT` when running the CLI so it picks the right project: `APP_VARIANT=unit npx eas-cli build --profile unit-production --platform ios`.
- Native folders are generated (CNG). Never commit `ios/`/`android/`; change native config only through config plugins in `@resgrid/config-plugins`.
- Use a per-variant Metro cache (or `--clear`) — the route root and `EXPO_PUBLIC_*` are inlined at transform time.

## Versions — derived from GitHub Actions, never backwards

- `M` = run number of Omni's `release.yml` (never rename that file — its counter is the source). Per variant, from the manifest: `version = <major>.M`, `versionCode` / iOS `buildNumber` = `<base> + M`, Electron semver `<major>.M.0`.
- Majors and bases (plan Appendix B): Responder **11** / 5100000, Unit **8** / 100000, IC **2** / 100000, Dispatch **2** / 100000, BigBoard **4** / 100000. They sit above every legacy build (legacy: Responder `10.N` / `5080345+N`, Unit `7.N` / `"7"+N`, IC `1.N` / `"1"+N`, Dispatch and BigBoard `1.N` / `N`).
- Versions are computed once in the release `plan` job and passed to build jobs as outputs.
- Tags are namespaced per variant: `responder-v11.x`, `unit-v8.x`, `ic-v2.x`, `dispatch-v2.x`, `bigboard-v4.x`.

## Web

- `APP_VARIANT=<v> npx expo export -p web --output-dir dist/<v>` — the same export feeds Docker and all three Electron jobs.
- `docker/Dockerfile` takes `ARG APP_VARIANT`; images keep their names (`resgridllc/{responder,unit,ic,dispatch,bigboard}`).
- Runtime config: `window.__ENV__` from `env-config.js`, **merged over** build env. The entrypoint also accepts legacy `${PREFIX}_*` names (`RESPOND_`, `UNIT_`, `IC_`, `DISPATCH_`, `BIGBOARD_`) so existing deployments keep working.
- nginx: no-store for `index.html` and `env-config.js`, deny dotfiles, CSP, Referrer-Policy, AASA/assetlinks, `/health`.

## Electron (`apps/desktop`)

- Thin package: electron, electron-builder, push receiver, updater. It loads `dist/<variant>` via the `app://bundle` protocol. Never add RN dependencies here (legacy installers were 387 MB because of that).
- Hardening (keep): CSP via `session.webRequest`, `will-navigate` origin guard, backslash rejection, deep-link queue, single-instance lock, external links opened in the OS browser.
- Per-variant appId, productName, protocol and icons come from the manifest; BigBoard keeps its loopback origin (`127.0.0.1:29317`) or migrates its localStorage.
- Targets: dmg + zip (x64/arm64, hardened runtime, notarized), NSIS + portable (signed), AppImage/deb/rpm. Auto-update channel per variant.
- Electron runs the **web** bundle; there is no Metro `electron` platform. Desktop-only behaviour goes through the preload bridges (`__ELECTRON__`, notifications, deep links, settings).

## CI build chain (GitHub Actions — plan §6.6)

- `ci.yml` (PR/merge queue): lint, type-check, translation parity, dependency-cruiser, Jest shards, API contract tests, per-variant `expo config` snapshot + route contract + web export smoke.
- `release.yml` (master merge → `production`, always native, publishes nothing to users; tag `<variant>-v*` → `production`; or dispatch): **plan** (versions, matrix, fingerprints) → per variant **web** export, **android** (two EAS builds: the AAB for Google Play, then the sideload APK attached to the release), **ios** (the App Store IPA only, for TestFlight and the App Store), each store package with its CycloneDX SBOM `<package>.cdx.json` (`scripts/ci/package-sbom.mjs`, advisory, from the kept EAS build directory) — every run builds native and none publishes an EAS update; the **fingerprint** job only records each platform's runtime in `fingerprints.json` → **docker** and **electron** (win/mac/linux) from the web artifact → **release** (GitHub Release `<variant>-v<version>` with every emit + `SHA256SUMS`, Firebase App Distribution for the APK, Changerawr, Electron update feed). **No store uploads from CI** (plan §15 #20): TestFlight and Google Play uploads are done by hand through the Software Factory (`int-RASF`). Never add `eas submit`, store credentials or a store-publishing workflow to Omni.
- **EAS updates are for critical and emergency fixes only** (owner decision 2026-11-10, plan §15 #23), never the regular way to deliver a release. Only `ota.yml` runs `eas update`, and only on the `hotfix` branch: a push to `hotfix` publishes to every variant's `production` channel; a dispatch from `hotfix` can pick variants, platforms and channel; any other ref is refused. Its guard (`scripts/ci/fingerprint.mjs check`) publishes a variant only when a release on the channel has binaries running the bundle's runtime (the newest such release, so a hotfix cut from the store build still reaches it after `master` built newer candidates). Never add `eas update` to another workflow or trigger (`scripts/ci/__tests__/hotfix-updates.test.mjs` guards it). Web and Electron get the same fix from a `release.yml` run.
- `nightly.yml`: Android dev-client builds and Android e2e (no iOS builds in CI).
- Rules: build each thing once (never rebuild the web app inside Docker or Electron jobs; never build dev clients on the release path); `fail-fast: false`; per-job timeouts; retries on network steps; release concurrency queues, PR concurrency cancels; signing material only in `$RUNNER_TEMP`, removed in an `always()` step.
- Electron updates use a generic feed per variant (`updates/<variant>/<channel>/`), not electron-updater's GitHub provider (five apps share one repo's releases).
- Secrets: one GitHub Environment per variant with identical secret names inside each (`EXPO_TOKEN`, `GOOGLE_SERVICES_JSON_BASE64`, `GRADLE_PROPERTIES`, Sentry DSN for that variant's own project…; no signing material, no store credentials and no App Store Connect API key for the mobile apps, see `docs/build/ci-secrets.md`). Never prefix-hack names in workflows. There is no MMKV key secret: storage keys are generated per device (plan D8).

## Config plugins and patches

- One copy of each plugin in `@resgrid/config-plugins`; a variant opts in through its manifest. Notables: Live Activities (team id from env, never hardcoded), `withRestrictedBootReceivers` (all variants; Android 15 boot-receiver crash), `withoutBackgroundLocation` (IC posture), icon badge, MediaButton/InCallAudio native modules, notification sounds.
- Icons, splash images and favicons are generated from vector masters (`node scripts/brand-assets/generate.mjs`), never hand-edited; badged icons must stay 1024×1024 (`pnpm variants:check`). Web/Electron splash lives in `apps/omni/public/index.html` and is stamped by `pnpm web:export`. → `docs/build/app-icons-and-splash.md`
- Android release builds run R8 (`enableMinifyInReleaseBuilds: true`; Google Play limits apps under 25% obfuscation). Adding or upgrading a native library means checking it for by-name reflection and adding keep rules to `androidKeepRules` in `app-config.js`; resource shrinking stays off (res/raw sounds are found by name). → `docs/build/google-play-checks.md`
- Patches via pnpm `patchedDependencies`, one copy each (`@gluestack-ui/core`, `react-native-webview`). Document why each patch exists next to it.
- Upgrades: use the `expo-upgrade` skill; one PR bumps the catalog and is verified by the full variant matrix.
